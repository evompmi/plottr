# tools/ — Architecture & conventions

Auto-loaded by Claude Code when work touches anything under `tools/`. Cross-cutting rules (code style, dev workflow, changelog policy) live in the repo-root `CLAUDE.md`.

## Tool structure

The repository ships **ten plot tools** (each in its own folder) and **two single-file calculators**, all served from a single hash-routed SPA: one `index.html`, one ReactDOM mount, one bundle.

- `index.html` — landing page **and** SPA entry. The static landing markup (top bar, hero with the four "how it works" steps as a full-width band at its foot, tools grouped by registry `category`, the dark "At the bench" calculator band, proof strip, cite footer — in that order) is HTML whose copy is swapped by `applyStaticI18n` (`_core/i18n/landing.{en,fr}.ts`). Tool links are plain `<a href="#/<tool>" data-tool>`; the SPA shell renders the matching tool into `<div id="root">`. **The hero shows real output only:** `tools/landing-specimen.svg` is `BoxplotChart` drawn from Group Plot's own `EXAMPLE_CSV`, the statistics beside it (`data-specimen`) are what Group Plot computes for it, and the comparison count (`data-benchmark-count`) is the R + SciPy total from `benchmark.html`. `tests/landing.test.js` regenerates all three through `tests/helpers/landing-specimen.js` and fails on drift; after an intended change run `UPDATE_LANDING=1 npx vitest run tests/landing.test.js`. "Try it on example data" links to `#/boxplot?example`, which `useExampleLink` (`_shell/useExampleLink.ts`) turns into the example on the plot step. On phones (≤ 900 px) the plot-tool groups, how-it-works strip and plot CTAs are hidden and a hint explains why; the calculators stay. A short inline IIFE near the bottom toggles `data-spa-route="active"` on `<html>` whenever a route is present, and CSS hides the landing accordingly. The top bar and footer row are shared with `privacy.html` and `benchmark.html` through `tools/site.css` (`.lp-top`, `.lp-nav`, `.lp-toggle`, `.lp-foot`); `benchmark.html` is generated by `benchmark/run.js`, so its page frame is edited in that template and the page regenerated with `node benchmark/run.js` (data unchanged).
- `benchmark.html` — generated public report comparing R 4.5 reference values vs. the migrated `tools/_core/stats/*` kernels (regenerated by `npm run benchmark`). Independent page; not part of the SPA.
- `privacy.html` — data-flow / trust page reachable from the privacy badge. Independent page.

**SPA shell** lives under `tools/_app/`:

- `tools/_app/Router.tsx` — minimal hash router (`useSyncExternalStore` over `window.location.hash`). Exposes `useRoute()` (returns the current route key or null) and `navigate(key)` (updates the hash, fires the `hashchange` event the router listens for). Hand-rolled, ~30 lines — `react-router-dom` is overkill for 10 fixed routes and would violate the no-runtime-CDN-deps stance.
- `tools/_app/tool-registry.ts` — single source of truth for the 10 tool routes. Each entry: `{ key, label, iconSvg, Component }`. Imports `App` from each tool's `app.tsx` (via `import { App as <Tool>App } from "../<tool>/app"`).
- `tools/_app/App.tsx` — top-level switcher. Reads the route, renders either a "landing placeholder" (route is null — only ever shown if the static landing's CSS hide-rule fails) or the tool component wrapped in `ErrorBoundary`. It builds the app-bar chrome — `BrandLink` (rune + wordmark, home), `ToolSwitcher` (menu of every tool grouped by its registry `category`: compare / trends / sets / bench) and the theme / language / feedback buttons — and hands it to each mounted tool through `AppChromeContext` (`_shell/AppBar.tsx`), because `_shell/` may not import the registry or router. Plot tools draw the `AppBar` inside `PlotToolShell`; for the two calculators (`category: "bench"`) `App.tsx` renders it directly. The calculators carry no in-page title (their name is in the switcher; a visually hidden `<h1>` keeps the outline) and wrap their content in `.dv-calc`, which `components.css` gives 44 px touch targets at ≤ 600 px; at that width the app bar drops the wordmark, divider and switcher icon to stay on one row.
- `tools/_app/index.tsx` — single ReactDOM mount + registers `window.__plottrSpaNavigate = navigate` so `navigateToTool` (`_shell/handoff.ts`) can switch tools in place when a cross-tool handoff fires.

**Plot tools — folder-per-tool layout** (`tools/<tool>/app.tsx` is the SPA-importable entry):

Each plot folder owns roughly:

- `app.tsx` — exports `function App()`. Imported by `tools/_app/tool-registry.ts`. The single ReactDOM mount lives in `tools/_app/index.tsx`; per-tool `app.tsx` files do not call `ReactDOM.createRoot`.
- `chart.tsx` — the SVG renderer (kept as `forwardRef`).
- `controls.tsx` — sidebar / tile components (per-tool).
- `steps.tsx` — UploadStep / ConfigureStep / FilterStep / OutputStep wrappers.
- `helpers.ts` — pure helpers (math / layout / label disambiguation). Imported by the tool's test loader (`tests/helpers/<tool>-loader.js`); a tool may also have a `helpers/` folder with multiple files re-exported through `helpers.ts` as a barrel (see `tools/venn/`).
- `plot-area.tsx` (where applicable) — composes chart + overlays + stats panels.
- `stats-panel.tsx` (where applicable) — the in-app statistics tile.
- `reports.ts` (where applicable) — R-script export builder for that tool.
- `howto.tsx` — the per-tool How-to content rendered through `_shell/HowTo.tsx`. The "Data layout" card can show the expected input with `HowToExampleTable` (headers, a few rows, optional "…" row, highlighted columns, caption) — Proportions and qPCR do.

**Calculators — flat layout** (no folder, no plot scaffold):

- `tools/molarity-app.tsx` — molarity / dilution / ligation prep sheets. Self-contained; does not use the plot-tool scaffold.
- `tools/power-app.tsx` — statistical power analysis (t / ANOVA / χ² / correlation). Self-contained because it has no upload step / column-role flow.

Both calculators export `function App()` exactly the way the plot tools' `app.tsx` files do; `tools/_app/tool-registry.ts` imports them via `import { App as PowerApp } from "../power-app"` etc.

**Build**: `npm run build` runs `esbuild tools/_app/index.tsx --bundle --splitting --format=esm --outdir=tools/_app --chunk-names=chunks/[name]-[hash] --jsx=transform --minify-syntax --minify-whitespace --sourcemap`. Single entry point, code-split output: `tools/_app/index.js` plus one lazy chunk per tool under `tools/_app/chunks/`. Each tool's `App` is wrapped in `React.lazy` inside `tool-registry.ts`, so the user only downloads the chunk for the route they visit.

## Shared code

The shared kernel lives as ES modules under `tools/_core/`. esbuild
bundles each module into the SPA entry (`tools/_app/index.tsx`) via
side-effect imports at the top of that file. Every tool caller imports
its kernel symbols directly via `import { parseRaw, … } from
"../_core/csv"` (or the appropriate sub-module); the `_core/*` modules
emit pure `export` declarations with no `globalThis` writes (the one
exception is `_core/svg-export.ts`'s `_svgExportMutators` WeakMap, which
deliberately lives on `globalThis` so two independently-bundled copies of
the module share a single registry).

The standalone HTML pages (`index.html`, `benchmark.html`, `privacy.html`)
also load `tools/shared.bundle.js` via a synchronous `<script>` tag — this
artefact is the bundled `_core/shared-bundle-entry.ts`, which re-exports
both `_core/theme.ts` and `_core/i18n.ts` (so the no-FOUC inline IIFE in
each `<head>` has the theme controls **and** the language wiring available
before the SPA module bundle parses, and the static landing can call
`applyStaticI18n` / `setLang` directly). The bundle is regenerated by
`scripts/build-shared.js` in `prebuild` / `prewatch` / `pretest` and is
checked into git for the static GitHub Pages deploy. Its `globalName` is
`__plottrShared` and the synthetic `Object.assign(globalThis, …)` footer
exposes every theme + i18n named export to the pages' inline scripts.

### Modules under `tools/_core/`

- **`tools/_core/shared.ts`** — color helpers, palette + diverging-palette catalogue, tool icons, numeric detection (`isNumericValue`, `toNumericValue`, `normalizeNumericString`), decimal-comma-aware free-text parsing (`parseDecimal`, used by the calculators), spread-free array extrema (`arrayMin`, `arrayMax` — use these instead of `Math.min(...arr)` on data-sized arrays, which throws past ~125k elements), seeded RNG, axis tick generators (`niceStep`, `makeTicks`, `makeLogTicks`), separator detection (`autoDetectSep` + `tokenizeDelimited`), decimal-comma fix (`fixDecimalCommas`), CSV / TSV parsing (`parseRaw`, `parseData`, `parseWideMatrix`, `wideToLong`, `reshapeWide`, `parseSetData`, `parseLongFormatSets`), descriptive stats (`computeStats`, `quartiles`, `kde`, `computeGroupStats`), SVG export (`buildExportSvg`, `serializeSvgForExport`, `appendPlottrAttribution`, `registerSvgExportMutator`), download helpers (`saveBlob`, `downloadSvg`, `downloadPng`, `downloadCsv`, `downloadText`, plus the batch variants `saveBlobs` / `downloadSvgs` / `downloadPngs` / `downloadCsvs` / `downloadTexts`), formula-injection scanner (`scanForFormulaInjection`).
- **`tools/_core/theme.ts`** — theme toggle wiring + `ThemeToggle` React component (`getTheme`, `setTheme`, `toggleTheme`, `useThemeMode`). Bundled into `shared.bundle.js` via `_core/shared-bundle-entry.ts` because the inline no-FOUC IIFE in each HTML `<head>` needs theme state available before the SPA module bundle parses.
- **`tools/_core/i18n.ts`** — i18n primitive + `LangToggle` React component, the twin of `theme.ts`. Translation lookup (`t`, `registerCatalog`, `useLang`, `useT`) with `{var}` interpolation and `Intl.PluralRules` plurals; language state (`getLang`, `setLang`, `toggleLang`) persisted under `plottr-lang` in localStorage with BroadcastChannel cross-tab sync; `applyStaticI18n` for the `data-i18n`-annotated static pages. Also bundled into `shared.bundle.js` (so the `<head>` snippet pins `<html lang>` no-FOUC and the landing can swap copy). Catalogs are registered per namespace — `core` / `shell` / `landing` eagerly, one per tool lazily via `import "./i18n"` in each `tools/<tool>/app.tsx` so they code-split into that tool's chunk. Both locales ship in the chunk (no per-locale fetch — keeps `file://` / offline working).
- **`tools/_core/shared-bundle-entry.ts`** — thin aggregator that `export *`s `theme.ts` + `i18n.ts`; the single entry point esbuild bundles into `tools/shared.bundle.js`. Add a primitive here only if the static HTML pages need it before the SPA parses.
- **`tools/_core/zip.ts`** — dependency-free ZIP archive builder (`buildZip`), method 0 / STORE, no ZIP64. Used internally by `download.ts`: when a `saveBlobs` batch exceeds three files it bundles them into one `.zip` rather than scattering downloads. A leaf module — imports nothing (declares its own `ZipEntry` shape) so it can't cycle with `download.ts`.
- **`tools/_core/stats/`** — statistical kernels, split across five sub-modules with a barrel re-export in `index.ts`:
  - **`stats/dist.ts`** — distributions + special functions + `bisect` + power calcs.
    - Distributions: `normcdf` / `normsf` (port of R's `pnorm`, Cody 1993), `norminv`, `tcdf`, `tinv`, `fcdf`, `chi2cdf`, `chi2inv`, `nctcdf` (port of R's `pnt`, AS 243), `ncf_sf`, `ncchi2cdf`
    - Exact rank-statistic nulls: `pwilcox`, `pkendall`, `prho` (ports of R's `pwilcox` / `pkendall` / `prho`, AS 89)
    - Special functions / helpers: `gammaln`, `betai`, `betacf`, `gammainc`, `gammainc_upper`, `bisect`
    - Power: `powerTwoSample`, `powerPaired`, `powerOneSample`, `powerAnova`, `powerCorrelation`, `powerChi2`, `fFromGroupMeans`
  - **`stats/tests.ts`** — descriptive helpers + parametric / nonparametric tests + effect sizes (depends on `stats/dist.ts`).
    - Descriptive: `sampleMean`, `sampleVariance`, `sampleSD`, `rankWithTies`
    - Tests: `shapiroWilk`, `leveneTest`, `tTest`, `mannWhitneyU`, `oneWayANOVA`, `welchANOVA`, `kruskalWallis`
    - Correlation: `pearsonCorrelation`, `spearmanCorrelation`, `kendallTau`, `selectCorrelation`
    - Effect sizes: `cohenD`, `hedgesG`, `rankBiserial`, `cohenDCI`, `cohenDUnpooled`, `cohenDUnpooledCI`, `etaSquared`, `epsilonSquared`
  - **`stats/posthoc.ts`** — studentized-range distribution + post-hocs + p-adjust + CLD + auto-picker (depends on `stats/tests.ts`).
    - Studentized range: `ptukey`, `qtukey` (plus internal `_wprob`, `_wprob_upper`, `ptukey_upper`)
    - Post-hocs: `tukeyHSD`, `gamesHowell`, `dunnTest`, `bhAdjust`
    - CLD + dispatcher: `compactLetterDisplay`, `selectTest`
  - **`stats/format.ts`** — `pStars`, `formatP` (zero-dep p-value formatters; lives alone so `tests.ts` and `posthoc.ts` can both consume them without drawing a cycle).
  - **`stats/cluster.ts`** — distance + clustering primitives used by `tools/heatmap/`. No intra-stats deps.
    - `pairwiseDistance`, `rowDistance`, `hclust`, `dendrogramLayout`, `kmeans`
  - **`stats/msi.ts`** — multi-set intersection probability for `tools/upset/` (depends on `stats/dist.ts`).
    - `multisetIntersectionP`, `multisetIntersectionPExact`, `multisetIntersectionPExactLower`, `multisetIntersectionPPoisson`, `multisetIntersectionExpected`, `multisetExclusiveExpected`, `multisetExclusiveP`
  - **`stats/types.ts`** — shared interfaces (`TTestResult`, `ANOVAResult`, `KruskalWallisResult`, `HClustResult`, `KMeansResult`, …) consumed by the kernel modules and re-exported through the barrel.

### Shared code constraint

**Add new shared helpers under `tools/_core/`** as TypeScript modules — strict types, real `export` declarations, no script-scope globals. Every caller imports the symbol directly; don't reach for `globalThis` writes. (If a helper genuinely needs to be a singleton across separately-bundled copies of the module — like `_core/svg-export.ts`'s `_svgExportMutators` WeakMap — store it on `globalThis` under a `__plottr…` namespace key. That pattern is for cross-bundle state correctness only.)

**`tools/shared.bundle.js` is auto-generated** by `scripts/build-shared.js` from `_core/theme.ts`. The script runs in `prebuild` / `prewatch` / `pretest`, so any local `npm run build` / `npm test` invocation regenerates the bundle. Don't edit `shared.bundle.js` by hand and don't add files to it — point new theme-adjacent code at `tools/_core/theme.ts` and let esbuild handle the bundling.

The bundle is checked into git (same convention as the compiled tool `.js` files) so the static GitHub Pages deploy keeps working without a server-side build.

## Theming (light / dark)

Theme switching is driven by CSS custom properties on `:root`, toggled via a `data-theme="dark"` attribute on `<html>`. The full palette lives in `tools/theme.css` (source of truth for every variable). Theme state is persisted in `localStorage` under `dataviz-theme`; a no-FOUC inline `<script>` in every HTML `<head>` reads it synchronously before first paint. On the very first visit with no stored choice, the `prefers-color-scheme` media query decides. A theme button lives in the app bar (every tool) and in the landing's top bar; `BroadcastChannel` syncs toggles across all open same-origin tabs (with the `storage` event as a fallback for browsers / contexts that drop BroadcastChannel).

**Language follows the same pattern.** i18n (`_core/i18n.ts`) mirrors this wiring exactly: language state persisted under `localStorage` key `plottr-lang`, a no-FOUC `<head>` snippet pinning `<html lang>` synchronously, `prefers`-style first-visit detection from `navigator.language`, a `LangToggle` (EN | FR) component, and BroadcastChannel + `storage` cross-tab sync. Both `theme.ts` and `i18n.ts` ship in `tools/shared.bundle.js` (see "Shared code" above). Their top-level listener side-effects are idempotent, so the double-run from being both script-tag-loaded and ES-module-imported (App.tsx imports both) is harmless.

**Chrome accent + typography.** The chrome is a cool grey ground (`--page-bg: #f3f4f7`), white surfaces, near-black ink (`--text: #15171c`) and one accent, Plöttr blue `--accent-primary: #3558d4` (~6:1 white text), used for the primary button (`--cta-primary-bg`) and the current step (`--accent-primary-weak` pill); in light mode link text (`--link`) and focus outlines (`--focus-outline`) are the same blue. `--accent-primary-hover` is its hover shade. The brand rune keeps its lighter `#648fff` stroke. Blue marks actions, links, the current step and focus; the **selected option of any pick-one control** (segmented toggles, On/Off pairs, the plot-style icon picker, the calculators' "solve for" lists) is ink (`--seg-selected-*`), never blue — `tests/theme-tokens.test.js` fails on a hand-built toggle whose active fill is an accent. Checkboxes keep the blue `accent-color`. Shape tokens: `--radius-sm/md/lg/xl` (4/6/8/12 px) and control heights `--control-h` (36), `--seg-h` (30), `--tab-h` (44). Three type tokens carry the voice: `--font-ui` (IBM Plex Sans) for all chrome, `--font-mono` (IBM Plex Mono) for numbers, statistics, file names, hex codes and the small uppercase section labels (`.dv-tile-title`), and `--font-display` (Fraunces) for the wordmark and landing headings only. All three fonts are **self-hosted**: `tools/fonts.css` declares `@font-face` against woff2 files under `tools/fonts/`, vendored by `scripts/vendor-fonts.mjs` (run manually when the font set changes — it is _not_ wired into the build, to keep the build network-free; run Prettier on `tools/fonts.css` afterwards). The app therefore makes zero third-party font requests, matching the SRI-pinned `vendor/react` stance; `@font-face` can't carry an SRI hash, so self-hosting _is_ the integrity guarantee. **Chart-internal SVG text is exempt** — it keeps its own hardcoded `font-family` (`sans-serif` / `monospace`) so exported SVG/PNG render identically off-DOM, the same way chart colours stay hex literals.

**Text vs fill tokens.** Accent and CTA tokens (`--accent-*`, `--cta-*`) are _fills_ and follow the dimmer-in-dark rule, so they must never colour text: in dark mode they sit near 2:1 on the surfaces. Text in an accent hue uses a text token, lighter in dark: `--link` (blue), `--dna-text` (violet), `--role-group-text` / `--role-value-text` / `--role-filter-text` (column roles; `roleTextColors` in `_core/color.ts`, while `roleColors` keeps the hues for borders and checkboxes), `--warning-text` / `--danger-text`. Chrome text drawn on a white plot card uses `--plot-card-text-muted` (not overridden in dark). Data-palette colours never colour text either: show them as a swatch next to the word (`StatsTable`, UpSet's bar legend). Keyboard focus rings use `--focus-outline` (the accent in light, a periwinkle in dark, ≥ 3:1 on every surface); `--focus-ring` is the older box-shadow glow used by Venn's rename field.

**Token tests.** `tests/theme-tokens.test.js` parses `tools/theme.css` and fails if any chrome text/background pair drops below 4.5:1 in either theme, if `--focus-outline` drops below 3:1 on any surface, if a token is declared twice in one block (the later copy silently wins), if the `prefers-color-scheme` dark block stops mirroring `[data-theme="dark"]` exactly, or if a dark `--accent-*` / `--cta-*` fill is brighter than its light counterpart (`--accent-blue` is the documented exception).

**Rule for contributors: chrome colors use `var(--name)`, SVG colors stay as literals.** Every inline `style={{ … }}` on a React element that is _not_ inside a chart component (`<svg>`, `<rect>`, `<path>`, `<text>`, etc.) must reference CSS variables so it themes correctly. Element fills, strokes, and text fills _inside_ SVG must stay as hex literals so exported SVG/PNG charts render the same way on any reader — the plot card wrapping each chart is hard-coded to `var(--plot-card-bg)` which resolves to white in both themes, so charts always sit on a white canvas.

Two custom ESLint rules together enforce the chrome / SVG split:

- **`plottr/no-chrome-hex-literal`** (`scripts/eslint-rules/no-chrome-hex-literal.js`) fires on any inline `style={{ key: "#abc..." }}` JSX attribute outside an SVG subtree. SVG element ancestors (svg / g / rect / path / line / circle / ellipse / text / polyline / polygon / tspan / defs / linearGradient / radialGradient / stop / clipPath / mask / marker / use / image / foreignObject / pattern) are exempt — chart internals legitimately use hex literals.
- **`plottr/no-css-var-in-svg`** (`scripts/eslint-rules/no-css-var-in-svg.js`) fires the inverse direction: a `var(--…)` reference inside an SVG element's `fill` / `stroke` / `color` (or the equivalent `style={{ fill: "var(--…)" }}` style prop) is flagged. The variable resolves correctly on screen but does not survive SVG export to viewers without DOM context (Inkscape, embedded preview, the browser's "open SVG file directly" path with a stripped CSS env), and the element falls back to default fill — silently broken charts with zero feedback at edit time.

**Coverage shape — read carefully.** Both rules see JSX inline `style={{...}}` (and `fill=` / `stroke=` / `color=`) literals, including dynamic-but-still-literal values nested _inside_ those literals: ternaries (`background: cond ? "#abc" : "..."`), short-circuit operators (`&&` / `||`), and template-literal static fragments. The rules do **not** see: (a) **identifier-ref** styles — `style={someStyle}` or `fill={someColor}`, where the value is a `const` defined elsewhere; (b) **spreads** — `style={{ ...base, ... }}`, since the spread members are opaque; (c) `React.createElement(..., { style: {...} })` calls inside any plain-JS helper file — those emit no `JSXAttribute` AST nodes the rule binds to, even though the runtime CSS rendering is identical; (d) `tools/components.css` and any other `.css` file — CSS isn't lint-targeted at all. When you abstract a colour into a `const styleObj = {...}` or a CSS class you've moved the literal _out_ of the rule's view; the leak is still there, the rule just stops complaining. If you touch one of those off-rule patterns — adding a new shared `.js` helper, editing `components.css`, or refactoring inline styles into a `const` — do the manual check yourself.

Common variables: `--font-ui`, `--font-display`, `--font-mono`, `--page-bg`, `--surface`, `--surface-subtle`, `--surface-sunken`, `--text`, `--text-muted`, `--text-faint`, `--border`, `--border-strong`, `--border-subtle`, `--accent-primary`, `--accent-primary-hover`, `--link`, `--accent-plot`, `--accent-dna`, `--on-accent`, `--plot-card-bg`, `--plot-card-border`, `--info-bg`/`--info-text`/`--info-border`, `--success-bg`/`--success-text`/`--success-border`, `--warning-bg`/`--warning-text`/`--warning-border`, `--danger-bg`/`--danger-text`/`--danger-border`, `--neutral-bg`/`--neutral-text`, `--subhead-bg`/`--subhead-text`, `--canvas-bg`/`--canvas-dot`, `--shadow-sheet`, `--inverse-bg`/`--inverse-text`, `--seg-selected-bg`/`--seg-selected-text`, `--dna-text`, `--role-*-text`, `--plot-card-text-muted`, `--focus-outline`. See `tools/theme.css` for the full list and the dark overrides.

## Data flow

File upload/paste -> `autoDetectSep` + `fixDecimalCommas` + `parseRaw` -> `DataPreview` table -> user assigns column roles -> `computeStats`/`quartiles` -> React SVG rendering -> SVG/CSV export

**Ingest size policy:** any new ingest surface (paste textarea, URL fetch, clipboard handler, …) must gate on `FILE_LIMIT_BYTES` (2 MB hard reject) and `FILE_WARN_BYTES` (1 MB warn) from `tools/_shell/FileDropZone.tsx` and surface the same red-banner UX `FileDropZone` uses. Import both names from `_shell/FileDropZone` (or the `_shell` barrel) — don't redeclare a local 2-MB number.

## Tool-internal structure

Plot tools live as folders (`tools/<tool>/`); calculators live as single files (`tools/molarity-app.tsx`, `tools/power-app.tsx`). Inside a plot-tool folder the convention is:

1. **Chart component** in `chart.tsx` (e.g. `BoxplotChart`, `BarChart`, `ScatterChart`) — the SVG renderer, kept as `forwardRef`.
2. **Step sub-components** in `steps.tsx` — `UploadStep`, `ConfigureStep`, `FilterStep`, `OutputStep` etc.
3. **Control components** in `controls.tsx` — the tool's `PlotControls`, a `ControlTabs` (2–4 tabs named by intent: Data / Groups, Style, Facets / Layout, Axes) whose tiles are `ControlSection`s.
4. **Pure helpers** (math / layout / label disambiguation) in `helpers.ts`. These are what the test loader picks up; if they get sprawling, split into a `helpers/` folder and re-export from `helpers.ts` as a barrel (see `tools/venn/`), or into named sibling modules the loader bundles alongside (boxplot: `layout.ts` chart geometry, `scales.ts`, `derive.ts` — App's data derivations: category order, group building per facet / subgroup cell, stats-panel sets, composition tables).
5. **App()** in `app.tsx` — orchestrator holding state and routing between steps. **`app.tsx` exports `App` and does NOT call `ReactDOM.createRoot`** (the single mount lives in `tools/_app/index.tsx`). Keep `app.tsx` slim: module-scope `VIS_INIT_<TOOL>`, the `EXAMPLE_CSV` / `EXAMPLE_TSV` sample-data const (see below), `function App()`, and `export { App };`. Tile / control / chart / step components belong in their own files.
6. **Plot-step composition** in `plot-area.tsx` (where applicable) — fills the `WorkspaceLayout` slots: `controls` (from `controls.tsx`), an optional `toolbar` (display toggles such as marks on plot, or a file / result summary), the `figure` (chart in a `.dv-plot-card` sheet plus chart-adjacent tables) and, for tools with statistics or per-item tables, the `inspector` (stats panel). Imported by the `PlotStep` JSX in `steps.tsx`.

**Layout exceptions** — these tools intentionally deviate from the 1–6 layout; each divergence is stable and not a regression. Use the canonical layout for new tools, but don't treat these as cleanup targets without a concrete reason:

- **`tools/aequorin/`** has the longest `app.tsx` (~2,000 lines), but ~1,200 of them are the inline `EXAMPLE_TSV` luminescence trace the sample-data convention below requires; `App()` itself (~700 lines, including the Ca²⁺ calibration and per-replicate Σ-integral memos) is in line with other tools. Not a cleanup target.
- **`tools/upset/`** has no `plot-area.tsx`. The chart + sidebar composition lives in `upset/steps.tsx` under the same `ConfigureStep` that handles upload + role-pick → configure → plot, because UpSet's "configure" and "plot" steps share a single mounted chart (you tune intersections by clicking the chart, not by toggling a separate plot step).
- **`tools/qpcr/`** has no `plot-area.tsx` (`PlotStep` in `steps.tsx`) and its own `stats-panel.tsx`, which calls the shared stats engine (`selectTest`, `runTest` / `runPostHoc`, `buildSelectTestReason`) per target gene on ΔCt rather than wrapping `StatsTile`. It has no hand-off to Group Plot: display options (bars / dots / boxes, orientation, a custom value range shared by every panel — typed in the units the tick labels show and converted by `parseAxisBound` — and an axis title) live in its own sidebar tiles, named like Group Plot's: Chart and Colours open, then folded Shape & fill / Data points / Axes & labels / Layout & background (`qpcr/controls.tsx`).
- **`tools/proportions/`** has no `plot-area.tsx` either — `PlotStep` lives in `steps.tsx` — and adds `stats-panel.tsx` (`StatsPanel` + `GofPanel`). It does not use `StatsTile` / the stats registry: those are built for numeric groups, while this tool tests a contingency table. It receives hand-offs from Group Plot's composition pies: `buildCompositionTables` (`boxplot/derive.ts`) turns the pies into one counts table per facet, groups labelled `facet.subgroup.group`; Proportions skips to the plot and shows a banner naming the class and group columns.
- **`tools/volcano/`** has no `plot-area.tsx`. The composition lives in `volcano/steps.tsx` as `PlotStep`. Volcano's plot step is short enough (one `WorkspaceLayout` with four control tabs, the summary strip as toolbar, no inspector) that a separate plot-area module would only add an import indirection.

**Sample-data convention — "all-(C)" / inline at module scope.** Every plot tool's `app.tsx` exposes a "Try sample data" button. The dataset that powers it lives as a ``const EXAMPLE_CSV = `…`;`` (or `EXAMPLE_TSV` for tab-separated, or `(() => { … })()` if procedurally generated) at the **top of `app.tsx`**, immediately after the imports and before `App()`. The button's handler is a `useCallback` named `loadExample` that calls `setSepOverride(",")`, `setFileName("…")`, and `doParse(EXAMPLE_CSV, ",")`. This convention is non-negotiable and applies everywhere — `aequorin`, `boxplot`, `heatmap`, `lineplot`, `proportions`, `qpcr`, `scatter`, `upset`, `venn`, `volcano`. (`proportions` also ships a second constant, `EXAMPLE_F2_CSV`, loaded by a tool-local button under the upload panel for the goodness-of-fit demo.) Why it matters:

- **Grep-discoverable.** A new contributor finds every example dataset in the codebase with `grep -nE "^const EXAMPLE_(CSV|TSV)" tools/*/app.tsx`.
- **Single failure mode.** Sample-data buttons either work (const is in scope) or compile-fail (typo in the const name). They cannot silently no-op.
- **No cross-cutting plumbing.** Sample data is a per-tool concern; it does not belong in `_core/shared.ts`, in a separate `_example.js` script tag, or in any `window`-global setup.

The presence of `EXAMPLE_CSV` / `EXAMPLE_TSV` at the top level of every `tools/*/app.tsx` is enforced by the `plottr/require-example-const` ESLint rule (`scripts/eslint-rules/require-example-const.js`). A future plot tool that gets through review without one will fail CI lint.

If a sample dataset is genuinely large or is shared across two tools, make the duplication explicit (literal copy in each `app.tsx`) rather than introducing a shared helper. The discoverability win beats the DRY win.

## Shared plot-tool scaffold (`tools/_shell/`)

All ten plot tools (Aequorin, Boxplot, Lineplot, Scatter, Heatmap, Venn, UpSet, Volcano, Proportions, qPCR) use the shared scaffold under `tools/_shell/`. Unlike the plain-JS `shared-*.js` globals, these are TypeScript modules imported via `import { … } from "./_shell/…"` and resolved by esbuild when bundling each tool. The two calculators (`molarity-app.tsx`, `power-app.tsx`) intentionally do **not** use this scaffold — they have no upload step, no column roles, no step navigator, so the shell would be dead weight.

- `tools/_shell/usePlotToolState.ts` — `usePlotToolState<TVis>(toolKey, initialVis)` typed hook. Owns step state, upload fields (`fileName`, `parseError`, `sepOverride`, `commaFixed`, `commaFixCount`), and the `vis` reducer with auto-prefs persistence (`loadAutoPrefs` on init, `saveAutoPrefs` on change, `_reset` sentinel for reset-to-defaults).
- `tools/_shell/handoff.ts` + `useHandoff.ts` — inter-tool hand-off (RLU timecourse → Group Plot, Group Plot → Proportions, Venn → UpSet). The source calls `setHandoff({ tool, … })` then `navigateToTool(tool)`; the destination calls `useHandoff(tool, apply)` once, which delivers payloads addressed to it at mount and on later writes (`plottr-handoff` event, SPA keep-alive), always through the latest `apply`. The payload lives in per-tab sessionStorage so a copy of the destination open in another tab can't consume it. Payloads not addressed to a receiver are left for their target; stale ones expire after `HANDOFF_TTL_MS`. A new destination tool uses the hook rather than its own listeners.
- `tools/_shell/PlotToolShell.tsx` — outer page frame. Renders the `AppBar` (sticky, full width) holding `StepNavBar` (inline: check for past steps, tinted pill for the current one, number for later ones), the loaded file's `FileChip`, and on the plot step the export bar (`PlotActionsBar`: Start over, then downloads, the SVG export last as the primary button) plus `PrefsPanel`. The bar stays on one row down to the 1100 px desktop floor in both languages: below 1560 px the file chip hides, below 1300 px the wordmark hides, "Download SVG" shows as "SVG" (`.dv-label-long` / `.dv-label-short`; the accessible name stays) and the gaps tighten (`components.css`). Below it come `CommaFixBanner` / `FormulaInjectionBanner` / `ParseErrorBanner` and the `children`. The bar publishes its height as the `--dv-sticky-top` CSS variable (only while visible — kept-alive tools are hidden, not unmounted). Each tool's `ActionsPanel` / `DownloadTiles` registers its downloads + reset through `PlotActionsContext` (`_shell/plot-actions.ts`) and renders nothing itself, so every tool's exports sit in the same place; exports belonging to a stats panel (R script / Methods / report) sit in that panel's `InspectorExports` footer. Every download other than the SVG figure (PNG first, then CSV / tables) sits in a "More" menu, so the bar shows only Start over, More and Download SVG. Steps other than plot render in a centred column; the plot step renders edge to edge for the tool's `WorkspaceLayout`. The body under the app bar is the page's `<main>` landmark (the calculators get theirs from `App.tsx`; the landing, Privacy and Benchmark pages have their own).
- `tools/_shell/ValueListPanel.tsx` — Group Plot's filter step: one card per group / filter column, one qPCR-style row per value (keep checkbox, inline rename, row count, ↑ / ↓). Rows never move when unticked or renamed: the tool keeps one stored order per column over every value (`orderableCols[i].fullOrder`, what `onReorder` receives), the plot order (`order`) is its kept subset, and `renameInOrder` (`boxplot/derive.ts`) moves a renamed value's slot to its new label. Two values renamed to the same label merge and move together.
- `tools/_shell/WorkspaceLayout.tsx` — the plot step's workspace: controls column (312 px) | dotted figure canvas with an optional `toolbar` row | `inspector` column (380 px, statistics); each column scrolls on its own below the app bar, and the side columns open with a visually hidden `<h2>` (their label) so the `h3` section titles inside sit in a valid outline. Leave `inspector` out for two columns. `InspectorSection` is one titled block of the inspector; `collapsible` (+ `defaultOpen`) turns its title into a disclosure button for repeated blocks, keeping the `right` badge visible when closed (qPCR: one block per gene, the first open). Every plot tool uses it; Group Plot is the reference (`PlotControls` as `ControlTabs` with Groups / Style / Facets / Axes, `BoxplotStatsDisplayBar` as the toolbar, `BoxplotStatsPanel` as the inspector). Tools with statistics put their stats panel in the inspector (RLU puts its Σ-barplot marks there too, since they only affect that barplot); UpSet and Venn put their intersection tables / item lists there; Heatmap and Volcano have two columns.
- `tools/_shell/Inspector.tsx` + `GroupTestSections.tsx` — the inspector's shared vocabulary: `inspectorTable` / `inspectorTh` / `inspectorTd` / `inspectorFirstCol` (compact mono tables), `StarsBadge`, `Verdict` / `AssumptionRow`, `ResultHeadline` (test name + stars + result parts), `SetRow` / `SetDetail` (selectable per-facet / per-x rows that open a set's sections) and `InspectorExports` (R script, Methods, report — all `dv-btn-secondary`). `GroupTestSections` renders a `selectTest` result's full section set (result + picker, assumptions, post-hoc, group summaries, replication planning) and is shared by Group Plot, Line Plot and RLU Timecourse; Scatter, qPCR and Proportions compose their own sections from the same pieces.
- `tools/_shell/ControlTabs.tsx` — the plot controls as an ARIA tablist (arrow keys, Home / End), the active tab remembered per tool under `localStorage` `plottr-tab-<tool>`. Inactive panels stay mounted. Inside a tab, `ControlSection` renders as an open titled group (`ControlTabsContext`) instead of a fold-out.
- `tools/_shell/ScrollablePlotCard.tsx` — horizontal-scroll affordances (edge fades + "Scroll for more →" pill driven by `ResizeObserver`). Used only by UpSet (`tools/upset/`); venn and heatmap intentionally don't wrap their plot cards (their charts auto-fit), so a plain `<div className="dv-panel dv-plot-card">` is correct there. Lift any new horizontally-scrolling tool into this component rather than re-deriving it.
- `tools/_shell/stats-dispatch.ts` — `runTest` / `runPostHoc` / `postHocForTest` dispatchers shared by boxplot, lineplot, and aequorin. Also exports the typed `TestResult` / `PostHocPair` / `PostHocResult` shapes (proper unions of the underlying test return-types, optional fields probed by presence) and a `testStatistic(res)` helper that pulls whichever statistic the result carries — collapses the per-test `if "t" in res / if "U" in res / …` chain to one call.
- `tools/_shell/methods-text.ts` + `MethodsButton.tsx` — the "📝 Methods" button in every stats panel (Group Plot, RLU, Line Plot, qPCR, Scatter, Proportions, UpSet) and on the Heatmap plot card. Opens a read-only popover with a methods-section paragraph built on demand from what actually ran (test, exact vs approximate p, post-hoc, corrections, n, display), closing with the Plöttr version, URL and the equivalent R calls. `buildGroupMethodsText` covers the `selectTest` engine; other tools assemble their own sentences (in their own i18n catalog) and finish with `alphaSentence` / `softwareSentence`. R one-liners come from `rTestCall` / `rPostHocCall` in `r-export.ts`, the same ones the R-script export uses. No references are added, and the text is not editable in place.
- `tools/_shell/chart-layout.ts` — `CHART_MARGIN` and `buildLineD` used by both lineplot and aequorin. Rule of thumb: once a pure typed helper becomes byte-identical across two tools, lift it here and re-export from each tool's `helpers.ts` barrel. `_shell/` is the canonical home for shared _component-tier_ helpers (React widgets, layout primitives, dispatcher tables); `_core/` is the canonical home for the shared _kernel_ (numeric, stats, parsing, theme).

**Standard wiring pattern** (every migrated tool follows this shape — start from `tools/upset/app.tsx` as the canonical reference):

```tsx
import { usePlotToolState } from "./_shell/usePlotToolState";
import { PlotToolShell } from "./_shell/PlotToolShell";

const { useState /* , useReducer, useMemo, ... */ } = React;

const VIS_INIT_<TOOL> = { /* persisted vis props */ };

function App() {
  const shell = usePlotToolState("<toolkey>", VIS_INIT_<TOOL>);
  const { step, setStep, fileName, setFileName, setParseError,
          sepOverride, setSepOverride, setCommaFixed, setCommaFixCount,
          vis, updVis } = shell;
  // tool-specific state (parsedRows, colRoles, filters, selection, …) stays local
  return (
    <PlotToolShell state={shell} toolName="…" title="…" subtitle="…"
                   visInit={VIS_INIT_<TOOL>} steps={[…]} canNavigate={…}>
      {/* step content */}
    </PlotToolShell>
  );
}
```

Key conventions:

- Hoist `VIS_INIT_<TOOL>` to **module scope** (not inside `App()`) so `usePlotToolState` can use it as both the reducer initial state and the `_reset` target.
- Tool-specific state (parsed rows, selection, tool-only reducers like boxplot's `statsUi` or heatmap's `cellBorder`) stays inline in `App()` — the scaffold intentionally does not become a kitchen sink.
- If a tool needs a dual-variant parse banner (e.g. aequorin's yellow "⚠️" warning vs. red error), keep `parseError` as **local** state and render the custom banner as `PlotToolShell` children; the shared `ParseErrorBanner` only renders the red error variant.

**esbuild flags matter.** The build command in `package.json` uses `--bundle --splitting --format=esm --outdir=tools/_app --chunk-names=chunks/[name]-[hash] --jsx=transform --minify-syntax --minify-whitespace --sourcemap`. `--bundle` inlines `_shell/*` imports into the entry / per-tool chunks; `--splitting` + `--format=esm` peels each `React.lazy(() => import("../<tool>/app"))` into its own lazy-loaded chunk under `tools/_app/chunks/` (also avoids the IIFE wrapping that would hide chart consts like `BoxplotChart` from render-smoke tests); `--minify-syntax --minify-whitespace` (not `--minify`) preserves top-level identifier names so the render harness can find them. Do not change these without also updating the render-smoke test harness.

**Test-loader pattern.** Per-tool test loaders (`tests/helpers/<tool>-loader.js`) bundle `tools/<tool>/helpers.ts` to CommonJS via `esbuild.buildSync` (`bundle: true` so cross-module imports inline cleanly), then evaluate the result under `vm.runInContext` with the shared kernel pre-loaded into the context. The kernel pre-load goes through `readCoreSharedSource()` (bundles `_core/shared.ts` to IIFE) and `readStatsSource()` (bundles the `_core/stats` barrel to IIFE) in `tests/helpers/_shell-test-utils.js`; each helper appends a synthetic `Object.assign(globalThis, __plottr…)` footer at bundling time so the vm context's `ctx.parseRaw` / `ctx.tTest` / etc. resolve exactly the way the old script-scope `shared.js` / `stats-*.js` files used to. (The `_core/*` source modules themselves emit no `globalThis` writes — the footer is a test-bundling concern, not a source-file concern.) Exports are read off a `module.exports` object threaded into the vm context via `ctx.module`. **If you add a new pure helper to a tool**, put it in `tools/<tool>/helpers.ts`, and add it to the `module.exports` block at the bottom of the matching loader — that's the only step; no slicing, no regex stripping.

**If you add a new plot tool**, start by copying the `tools/upset/` folder (or any other migrated plot tool) and adapting `chart.tsx` / `controls.tsx` / `steps.tsx` / `helpers.ts`. Do not re-derive the scaffold and do not stuff the whole tool into `app.tsx` — keep `app.tsx` to the `App()` orchestrator, the module-scope `VIS_INIT_<TOOL>`, and the inline `EXAMPLE_CSV` / `EXAMPLE_TSV`. Then add the new tool to `tools/_app/tool-registry.ts` so the SPA picks up its `/#/<toolkey>` route.

## Statistical methodology

The `tools/_core/stats/*` modules ship **three** small but consequential default-policy decisions for numeric data (plus the counts defaults below). Each is documented in the source comments of the affected function and each has benchmark coverage; the rule for contributors is "do not silently change them — they are user-facing methodological choices, not implementation details".

**Welch by default — `selectTest()` (`tools/_core/stats/posthoc.ts`).** Plöttr does not pre-screen with Shapiro-Wilk + Levene before picking between Student's t and Welch's t (or one-way ANOVA and Welch's ANOVA). It picks **Welch unconditionally**:

- `k = 2` independent groups → Welch's t (no post-hoc).
- `k ≥ 3` independent groups → Welch's ANOVA + Games-Howell post-hoc.
- Shapiro-Wilk + Levene are still computed and surfaced in the stats panel as **diagnostics**, with a `recommendation.suggestion` payload the user can click through to override (e.g. "your residuals look very non-normal — consider Mann-Whitney U / Kruskal-Wallis"). The default test stays Welch.

Why: the Rasch / Kubinger / Moder (2011) and Zimmerman (2004) results show that screening for equal variance with a pre-test inflates Type I error compared to using Welch's t unconditionally; Welch matches Student closely when variances are in fact equal, and behaves correctly when they are not. A "Student's t when Levene passes, Welch's t when it fails" policy is a methodological bug, not a stylistic choice.

If you change the default policy, you change the answer Plöttr gives users on the same data — that's a public-facing behavioural change and must land with: (a) a `CHANGELOG.md` entry under `Changed`, (b) a benchmark refresh confirming agreement with R / SciPy under the new defaults, and (c) a corresponding update to the recommendation `reason` text returned from `selectTest()` so the stats panel explains the new policy in plain English.

**Rank tests and effect sizes follow R's defaults.** `mannWhitneyU`, `spearmanCorrelation` and `kendallTau` report what `wilcox.test` / `cor.test` report by default, each pinned to R in `tests/stats.test.js` / `tests/correlation.test.js` and the benchmark:

- **Mann-Whitney**: exact p (`pwilcox`) when both n < 50 and there are no ties; otherwise the normal approximation with continuity correction. Results carry `exact`.
- **Spearman**: AS 89 on S = Σd² when there are no ties and n ≤ 1290 (exact enumeration for n ≤ 9, Edgeworth series above); otherwise the t approximation.
- **Kendall**: the exact distribution of T when n < 50 and there are no ties; otherwise the tie-corrected normal approximation. S comes from Knight's O(n log n) merge-sort count.
- **Cohen's d** (`_shell/power-from-data.ts`) mirrors `effectsize::cohens_d`: pooled SD for Student / Mann-Whitney, the unpooled √((s₁² + s₂²)/2) with a Welch-df noncentral-t CI for Welch (`pooled_sd = FALSE` — not Glass's Δ).
- **Correlation power** is a port of `pwr::pwr.r.test` (t-based critical r, r / (2(n − 1)) bias term on atanh r).

The R-script exports call `wilcox.test` / `cor.test` without `exact = FALSE` so they reproduce these numbers. `nctcdf` departs from R's `pnt` only toward the exact value (a tighter series tolerance, a direct integral for |δ| > 37.62 and for far lower tails where R's `pt` loses precision).

**Counts and proportions — `tools/_core/stats/categorical.ts`.** The Proportions tool's defaults, each pinned to R in `tests/categorical.test.js` and the benchmark:

- **Wilson score CIs** (`prop.test(correct = FALSE)$conf.int`), never Wald — Brown, Cai & DasGupta (2001), _Statistical Science_ 16(2), doi:10.1214/ss/1009213286. The normal quantile comes from `qnormPrecise` (AS 241, full double precision) rather than `dist.ts`'s Acklam `norminv`, so bounds match R to ~1e-15.
- **Test choice (`selectCountsTest`)**: 2×2 → Fisher's exact test always; larger tables → Pearson χ² (no Yates) when Cochran's rule holds (every expected count ≥ 1, ≤ 20 % below 5), Fisher otherwise. The user can override.
- **Two-sided exact p-values** use R's rule: sum P(outcome) over outcomes with P ≤ P(observed) × (1 + 1e-7) — `binomTest`, `fisherExact`, `multinomialExactGOF`. Never the "double the smaller tail" shortcut.
- **R×C Fisher** is a network enumeration (path merging on sorted remaining row totals, relaxed per-column bounds, sorted-completion lookup for the last free column) with a deterministic work budget (`FISHER_MAX_WORK`); past it, a seeded Monte-Carlo p (`FISHER_MC_B` tables, R's `(1 + hits) / (B + 1)`) flagged `method: "monteCarlo"` with its SE — the UI and report always say so. The 2×2 odds ratio is R's conditional MLE with its exact CI, solved to full precision (R's own `fisher.test` stops `uniroot` at ~1e-4).
- **Pairwise comparisons**: Fisher's exact test on each 2-row sub-table, **Holm** by default (`holmAdjust`), BH selectable. All pairs (`pairwiseFisher`) by default, or many-to-one against a user-picked control group (`pairwiseFisherVsControl`: k − 1 tests, adjusted over those only; letters are unavailable in that mode, brackets are drawn instead).
- **Goodness of fit**: exact multinomial (binomial for k = 2) when the outcome space is ≤ `MULTINOMIAL_EXACT_MAX_OUTCOMES`, else χ² (flagged `fallback`); Holm across groups.

**qPCR relative quantification — `tools/qpcr/helpers.ts`.** One formula covers 2^−ΔΔCt (Livak & Schmittgen 2001, doi:10.1006/meth.2001.1262) and efficiency-corrected ratios (Pfaffl 2001, doi:10.1093/nar/29.9.e45): per biological sample, log2 quantity q = −Ct̄·log2E; the reference is the mean q over reference genes (log of their geometric mean, Vandesompele et al. 2002, doi:10.1186/gb-2002-3-7-research0034); ΔCt = q_ref − q_target; −ΔΔCt = mean ΔCt(control) − ΔCt. All E = 2 reduces exactly to Ct_T − mean(Ct_ref). With "Normalise to: reference genes only" (`QpcrConfig.normalize = "refs"`) the calibrator is 0, so L = −ΔCt and the chart shows 2^−ΔCt (Schmittgen & Livak 2008, doi:10.1038/nprot.2008.73); tests are unchanged. Rules:

- **Statistics run on ΔCt, never on 2^−ΔΔCt** — through the Group Plot engine (`selectTest` → Welch t / Welch ANOVA + Games-Howell, override, decision trace). Fold changes are reported only as back-transformed estimates: per-group SEM / SD / 95 % t-CI of mean −ΔΔCt on the chart (`errorBounds`, log scale), Welch 95 % CI of the ΔCt difference vs control in the table.
- **Technical replicates** are averaged per (group, sample) × gene (missing Ct dropped); SD > 0.5 cycles is flagged. A sample missing the target or any reference is dropped and listed.
- **geNorm M** is shown as information only (lower = more stable). The 2002 paper defines M but gives no M cut-off (its only numeric cut-off is V < 0.15 for the number of genes), so the tool does not claim one.

**`recommendation.suggestion` is a UI contract, not a free-form string.** `selectTest` returns a structured object `{ chosen, reason, suggestion?: { test, why } }`. The boxplot stats panel wires this into a "Switch to suggested test" button — adding new fields requires updating the consumer in `tools/boxplot/stats-panel.tsx`. Don't smuggle UX cues into the `reason` string.
